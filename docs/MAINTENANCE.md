判断：本项目更合适的方向是“小而可审计的导师协作参考实现”。优先级应是权限一致性、依赖维护、可复现部署和清晰的管理员流程。预约排课、支付、营销与大而全的运营后台涉及额外规则和维护成本，不作为本轮默认扩展。

## 本轮落实

- 消息写入事务内重新读取发送者会话成员、订单归属和已指派导师审批状态；不再仅依赖事务前的判断。预览和未读数更新也重新核验接收者。
- 增加真实适配器回调的回归测试，覆盖审批撤销、订单改派、成员变化、重放以及写入失败回滚；测试仍不模拟真实 CloudBase 锁机制。
- CI 的本地测试运行时从 Node 20 调整为 Node 22/24 LTS，Actions 固定到已核对的完整提交 SHA，并关闭持久化 Git 凭据。参见 [Node 官方发布状态](https://nodejs.org/en/about/previous-releases)。云端运行时未更改。
- 为 14 个独立云函数提交锁文件，新增离线锁校验和在线依赖审计。相同依赖树合并查询；不同树分别检查。审计失败不会伪装为通过。
- 公开记录当前依赖告警与升级门槛，保留“本地通过”与“云端通过”的区别。

## 尚未完成，按优先级处理

1. **高优先级：SDK 升级候选的隔离云环境验收。** 4.0.2 加两个定向覆盖的候选已达到 0 审计告警，132 项仓库测试及 9 项真实 SDK 契约测试通过。数据库子库的事务请求变化、BSON 升级和云端安装器是否执行覆盖仍须实测；在候选分支完成审查与隔离验证后再合并。见 [依赖策略](DEPENDENCIES.md)。
2. **高优先级：隔离环境双账号实测。** 沿用 [Issue #1](https://github.com/YxCarl/yinjiao-bangbang/issues/1)，验证微信身份、事务竞争、索引、文件访问和规则。没有这一步，不能把 v0.2.0 或生产就绪标为完成。
3. **中优先级：管理员审批与审计流程。** 补齐审核人授权、决定记录、撤销操作和必要的数据保留规则；先确定个人信息最小化方案，再考虑后台界面。当前手工可信管理员流程仍为参考实现。
4. **中优先级：订单取消/争议与删除策略。** 明确进行中订单的退出方式、合成钱包与真实支付的界限、消息和附件保留期；需要业务规则选择，不直接引入真实支付。
5. **中优先级：当前版本演示与贡献者验收。** 在隔离环境生成新截图/短演示，补齐错误、空列表和权限变化状态；旧截图继续保留历史标注。
6. **维护治理：Issue 与保护规则。** #6 的本地适配器测试目标已有代码与测试证据；其状态需要有 Issue 写权限的维护者同步。#1 等真实环境待办不能据此关闭。本次 GitHub 连接返回 Issue 写入权限不足，因此未创建或关闭 Issue，待办保存在本文件和路线图中。建议单独评估 main 分支保护，不擅自改变现有合并权限。

## 建议维护节奏（人工执行，不代表已创建定时任务）

- 每月：检查开放 Issue、SDK 公告、`npm run audit:cloud`、Node 支持状态和文档链接。
- 每次代码修改：运行 `npm test`；依赖相关 PR/推送会自动触发独立审计；其余时间可在 GitHub Actions 手动运行 **Dependency audit**。
- 每次依赖升级：所有函数同步更新 manifest/lock，检查真实 SDK 兼容性，保留回滚版本。
- 每次发布：完成隔离环境矩阵，更新 CHANGELOG、ROADMAP 与脱敏证据，再创建标签。

流程不自动合并、不自动部署、不发送申请、不触碰历史环境。在线审计需要 npm 注册表网络访问；注册表不可达表示“未完成”，不是“无漏洞”。
